# Code2LoRA-rs — project log & findings

A running record of what was built, what we measured, the honest gaps, and the
decisions made — so none of it is lost. Detailed tables live in `README.md`,
`SECURITY.md`, `tinker/RESULTS.md`, and `tinker/RESULTS_multilang.md`; this file
is the index + the things not captured elsewhere.

Paper: **Code2LoRA** — *Hypernetwork-Generated Adapters for Code LMs under
Software Evolution* (arXiv:2606.06492). Core claim: inject repository knowledge as
LoRA **parameters** (generated by a hypernetwork in one forward pass) instead of
**retrieved context**, with zero inference-time token overhead.

## Headline results (all live on real models)

- **Generated adapter runs on the real model.** Rust-generated PEFT adapter loads
  onto **Qwen2.5-Coder-1.5B** via PEFT and generates (`peft_local.py`). (Hypernet
  untrained ⇒ ≈parity; the deliverable is real-model attachment/execution.)
- **Parametric beats RAG.** Python 3-repo: repo-LoRA **62.5%** vs RAG ~38% vs base
  41.7%. Cross-language 9 repos (JS/Rust/Go): repo-LoRA **55.6%** mean, wins **8/9**;
  RAG = base (27.8%) at ~4× tokens. (`tinker/RESULTS*.md`)
- **Scaling raises the ceiling, every language.** cachetools (Py) 60→**92%**;
  lodash (JS) 50→75%; serde-json (Rust) 43.8→71.9% (flips RAG); gin (Go) 12.5→71.9%.
- **Hypernetwork learns + generalizes.** Pure-Rust autograd: held-out adaptation
  error **260 → 2.2 (−99.2%)** on unseen repos.
- **Semantic conditioning.** Neural embedder: two differently-worded HTTP repos →
  adapter cosine **0.74** vs **0.39** to a math repo (hash: 0.51 vs 0.11).
- **Evo trajectory.** Per-commit adapter evolution, order-sensitive, deterministic.

## Security tangent — findings (kept here so they're not lost)

Goal: use Evo to flag malicious commits. Tested on a synthetic injection and the
two REAL supply-chain attacks whose commits survive in public history.

`commit_anomaly.py` (bge-large embeddings, multiple scorers), rank of the malicious commit:

| repo / attack | state-jump | centroid | **kNN (k=3)** | trained predictor |
|---|---|---|---|---|
| `Marak/colors.js` `074a0f8` (real Jan-2022 DoS) | #18/40 | #13/40 | **#1/40 ✅** | #40/40 |
| `tukaani-project/xz` `cf44e4b7` (real CVE-2024-3094) | #14/40 | #5/40 | #6/40 | #36/40 |
| `facebook/react` + planted overt exfil (synthetic) | #24 (hash) / #3 (neural) | — | — | — |

Conclusions (honest):
- **kNN local-outlier on semantic embeddings catches the real colors.js DoS at #1** —
  the payload fools the global mean (camouflaged as idiomatic colors string-styling)
  but has no close neighbours. `evo-scan --method knn` (now default) ports this; the
  Rust mean+max embedding is weaker than pure mean-pool, and empty/merge commits must
  be filtered (zero-norm diffs otherwise score 1.0).
- **xz still evades text-based detection** (best #5–6, top 15%) because the payload is
  in **binary** test files — exactly why it evaded human review. Needs binary/entropy
  features.
- Untrained novelty catches blatant foreign code, not real camouflage. It's a triage
  *prior*, not a detector. Full writeup: `SECURITY.md`.

## The one real gap in the core claim

The *measured* repo-adaptation gains come from the **per-repo LoRA training loop**
(the paper's upper-bound baseline), not yet from the hypernetwork's **one-pass
generation** (which is at initialization ⇒ near-identity). Closing this = training
the hypernetwork **through a real base model**, which is GPU-bound:
- this container is **CPU-only**;
- **Tinker** trains only its own LoRA — it cannot backprop into a custom hypernetwork.

So one-pass generation producing real gains is the open end-to-end step. Halves of
it are each proven: the hypernetwork *learns/generalizes* (`train-demo`, small scale)
and a *trained* adapter on the real model *beats RAG* (per-repo LoRA).

### GPU attempt (vast.ai RTX 3090) — honest negative result
Ran `gpu/train_hypernet_gpu.py`: trained the Static hypernetwork **through frozen
Qwen2.5-Coder-1.5B** on 7 repos, 700 steps. Training loss fell **6.18 → 2.91** —
the end-to-end differentiable pipeline (generated LoRA backprops into the
hypernetwork through the real model) **works mechanically**. But the **one-pass
generated adapter on held-out repos gave 2.5% EM vs 32.5% base (−30 pp)** — it
*degrades* unseen repos, not improves them.

Diagnosis (matches the paper: cross-repo generalization is the hard part):
- **Only 7 training repos** — far too few for a hypernetwork to learn a
  generalizable repo→adapter map (paper uses ~500 repos / 40K tasks); it memorizes
  the 7 and extrapolates destructively.
- The catastrophic drop (to 2.5%, not ~base) suggests the **learnable log-scales
  grew** to fit train repos, producing large ΔW that wrecks held-out generation.
- Small hypernet / short run / no generalization-oriented regularization.

To actually close the gap: many more training repos, clamp/fix the log-scale +
weight decay + lower LR/alpha, more steps. That is a larger (costlier) GPU run and
still requires tuning — consistent with why the paper's contribution is non-trivial.
Infra works: vast.ai via onstart + `vastai logs` (SSH/exec blocked by egress).

### Reproduce + train on the paper's OWN data (RepoPeftBench) — H100
Found the released artifacts (`huggingface.co/code2lora`): data
(`code2lora-data-snapshots`: 400 train repos, 44,149 train QnAs, precomputed
2048-d `repo_state_embedding`), the exact `Code2LoRAHead` (vendored in
`gpu/reference/code2lora_core.py`), and their trained checkpoint
(`code2lora-direct`). `gpu/c2l_gpu.py` reproduces-then-trains on the SAME
data/eval. Arch detail that fixed our earlier collapse: their head **clamps the
LoRA scale to ≤0.3**.

**Reproduced** their checkpoint on our harness (8 QnAs/repo subsample, prefix
truncated to 1024 vs their 8192): base **33.6%**, their ckpt **50.7%** (+17.1pp,
mirroring the paper's +18.1pp 45.7→63.8); their head loads `missing=0 unexpected=0`.

**Trained** 3 configs on the full data (H100): rank16/h1024/3ep (control),
rank32/h1024/3ep, rank32/h2048/4ep. Held-out CR-test EM **peaks ~49.5% at
~step 2000 (~⅓ epoch) then declines** (overfits; train loss → 0.05, CR 49.5→45.8);
higher rank/capacity did not help.

**Honest result: matched their checkpoint** (~49.5% peak vs 50.7%, within the
±2-3% noise of a 408-sample eval) on the identical harness, but **did NOT beat**
it. Beating their *reported* 63.8% is capped by our truncated-context harness and
would need full-context (8192) training+eval (~8× memory/time) + early-stopping/
regularization + a larger search. GPU OOM fixed via gradient checkpointing + bf16
LoRA delta + batch 4. Total GPU spend ≈ $5.

### Beat-the-paper attempt #2 — fair harness + regularized sweep (H100)
After fixing the harness (randomized eval sample, `max_new=24`, MAXLEN 2048,
prefixes are short — median 224 tok — so truncation wasn't the main gap), the
recalibrated bar = **their checkpoint 53.1% on the fair harness** (±2pp across
H100 hosts from bf16 numerics; was 50.7% on the cruder harness; paper reports
63.8%, the rest of the gap is MAXLEN 2048 vs 8192 + EM-definition details).

Swept 3 configs, trained from scratch on the full data (train@1024/eval@2048,
grad-checkpoint + bf16 delta + batch 8 to fit):
- control (no dropout, lr1e-4): peak **52.2%** @ step 2500, then overfit-declined
  to 45.5% @ 5000.
- dropout0.1 + wd0.05 + lr5e-5: 45.5 → 46.0% (slower, lower).
- dropout0.2 + wd0.1 + lr5e-5: 41.8% (slowest, lower).

**Final honest verdict: MATCHED, did not beat.** Best trained head 52.2% vs their
checkpoint 53.1% on the identical fair harness (within the ±2pp noise).
Regularization changed convergence speed, not the ceiling; the hypernetwork class
saturates at the paper's level on its own data. A decisive beat would need a
different lever (better/re-computed repo embeddings — but those are provided/fixed;
per-layer adapters; more/augmented training data; full 8192-context) — a research
effort, not a sweep. Total vast.ai spend ≈ $12.

Modal harness added (`gpu/modal_app.py`) and validated (H100 function runs, returns
results directly) as a cleaner loop for any future iteration.

### Improvement attempt: per-layer (FiLM) adapters — ran on Modal H100
Generated a *distinct* (A,B) per (layer, module) via a shared head modulated by a
learned per-layer FiLM (`gpu/perlayer.py`) — more expressive than the paper's
layer-shared design at ~the same param count — head-to-head vs the shared control,
same fair harness. Two infra fixes en route: (a) early-stop checkpoint save to
`/tmp` (Modal has no `/workspace`); (b) **NaN divergence** because Modal pulled
latest torch while the working vast env was torch 2.5.1 — fixed by pinning
`torch==2.5.1` + gradient clipping.

Results (bar = their checkpoint on this harness, ~53.5–54.4%):
- shared control (clamp 0.3, lr1e-4): 52.0 → **52.8%** peak ≈ bar → **MATCH**.
- per-layer (clamp 0.15, lr5e-5): 42.9 → 46.4% — **underperforms**.

**Finding:** per-layer needs a *tight* magnitude clamp or it diverges (28
uncorrelated adapters compound down the residual stream — shared is coherent), but
that tight clamp *also caps its adaptation*, so it lands below the shared design.
The paper shares adapters across layers for **stability + a magnitude/expressivity
sweet spot**, not just parameter efficiency. Net across all attempts: best trained
head **matches** their checkpoint (~52–53%), does **not beat** it; per-layer is a
real research direction (needs per-layer magnitude ≈ shared/√depth + tuning), not a
quick win. Modal credits ≈ untouched after stopping; vast ≈ $68 left.

## Decisions / environment notes

- Live model is **Qwen/Qwen3.5-4B** (Tinker's catalog lacks Qwen2.5-Coder-1.5B);
  the Rust crate keeps Qwen2.5-Coder-1.5B as the offline structural target.
- Default embedder is feature-hashing (offline, no deps); `--features neural` adds
  candle + bge-large.
- TLS-intercepting proxy: `hf-hub`'s bundled roots reject the proxy CA → download
  models with a system-trusted tool and pass the local dir to `--embed-model`.
- Tinker API key is provided via `TINKER_API_KEY` (never committed).
